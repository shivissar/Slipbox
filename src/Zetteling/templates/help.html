Help & reference

Everything you need to use this Zettelkasten. Open this page any time from the question-mark button at the bottom of the sidebar, or with ⌘K → “Help”.

The three things most people look up

If you came here with a specific question, these are the three most common ones:

  • Where do my notes live on disk? — short answer: the path shown under Folders on the settings page, labelled In use now.
  • How do I connect my Zotero library? — short answer: configure Better BibTeX in Zotero, export to a .bib file, paste the path into settings.
  • How do I back up my notes? — short answer: your notes are a folder of plain Markdown files; any backup tool works. Time Machine and Git are both fine. For multi-device sync, Syncthing.

Everything else in this page is either context for those three or coverage of a narrower question. The section navigation below links to each major topic.

Getting around (new in 5.0)

Zetteling is one window. The sidebar on the left holds your four kinds of note, tags, threads, citations and stats. Next to it is the note list for whatever you picked, then the note itself, and on the right a side panel with the note's thread, backlinks, related notes and the Interrogate tab. The panel button at the top right of a note hides or shows the side panel.

The command palette. Press ⌘K (or click Search in the sidebar) and start typing. It finds notes by title and text, and it runs commands: new note, edit, export, open another note beside this one, go to any page, switch between light and dark. Arrow keys move, ↵ opens, esc closes.

Linking and citing while you write. In the editor, type [[ and a picker appears at the cursor listing matching notes; press ↵ to insert the link, or ⇧↵ to insert it with the note's title as the link text. Type @ at the start of a word to search your bibliography the same way. The Links in this note list in the editor's side panel shows the titles of every note you have linked, so the 14-digit IDs never need reading.

Keyboard shortcuts
⌘K command palette · ⌘N new note · ⇧⌘N new journal entry · ⌘E edit this note · ⌘I interrogate this note · ⌘S save and close the editor · ⌘, settings · ⌘↵ send a message in Interrogate. If a shortcut does nothing on your Mac, a menu item may be using the same keys; the palette always works.

What is a Zettelkasten?

A Zettelkasten ("slip box" in German) is a note-taking method developed by the German sociologist Niklas Luhmann, who used it across forty years of work to produce around seventy books and four hundred peer-reviewed papers. His Zettelkasten contained roughly 90,000 paper slips. When asked how he was so prolific, Luhmann famously replied that he wasn't — his Zettelkasten was.

The method has four central principles, all of which this app is built around:

  1. Atomic notes. Each note expresses one idea, one observation, or one argument — not a topic, not a chapter, not a meeting summary. The unit is the smallest thing that can stand on its own. A note titled "Algorithmic governance erodes accountability" is atomic; a note titled "Notes on Aneesh's chapter 3" is not. The reason for atomicity is that small ideas combine and recombine in ways that large ones cannot — an atomic note about dissonance can show up unexpectedly in arguments about labor, surveillance, or affect, whereas a chapter summary can only be cited as itself.
  2. Links between notes are the structure. A Zettelkasten has no folder hierarchy. Notes are connected to each other by direct references — in this app, that's the [[id]] wikilink syntax. Over time the web of links becomes the structure: it grows organically from your actual thinking rather than from a category scheme you imposed in advance. The backlinks panel on every note shows what other notes have referenced it, which is how new connections surface.
  3. Notes are written in your own words. A Zettelkasten is not a quote collection. The act of rewriting an idea in your own words, in your own voice, is the moment of understanding. If you copy a passage verbatim, you have moved text from one place to another but you have not yet thought about it. Sonke Ahrens makes this argument forcefully in How to Take Smart Notes (2017): the friction of rewriting is the cognitive work, and shortcuts that bypass it (including AI-generated summaries) defeat the epistemic point of the method.
  4. The system serves long-term writing, not retrieval. A Zettelkasten is not a search engine for your past readings — for that you have Google Scholar and Zotero. It is a thinking partner across years. You write notes today not because you need them today, but because some future project will surprise you by drawing on them. This is why the method rewards consistency more than volume.

How this app maps onto the method. Wikilinks [[id]] are how you connect notes; backlinks (shown automatically on every note view) are how connections surface in reverse. Tags are a lightweight grouping mechanism for cross-cutting themes that don't deserve their own thread. Threads are this app's implementation of Luhmann's Folgezettel — sequential chains where notes follow each other in a deliberate argumentative order, and a single note can belong to multiple threads simultaneously. The citation system lets you reference Zotero entries by @citekey without copying their text — your notes stay in your voice, while pointing precisely at the sources behind your claims.

For deeper reading: Sonke Ahrens, How to Take Smart Notes (2nd ed., 2022); Luhmann's own brief essay Communicating with Slip Boxes (1981, translated by Manfred Kuehn); and the writing of Andy Matuschak on evergreen notes at notes.andymatuschak.org.

The basics

Every note is a single plain Markdown file in your notes folder. Zetteling is packaged as a desktop application via BeeWare — when you launch the app, it starts a local Flask server on an ephemeral port and opens a native window pointing at it. The web interface you are reading right now is one way to interact with those files; any text editor you like is another. The two are kept in sync automatically — edit a file in Obsidian, vim, or TextEdit and the index will update within a second or two.

Where your notes live. Out of the box, Zetteling stores notes inside its application-data folder, in the platform-standard location for your operating system. On macOS that's typically ~/Library/Application Support/com.shivissar.zetteling/notes/. The exact active path is always shown under Folders on the settings page, labelled In use now. This default works fine for daily use but is awkward for syncing across devices — see Sync & backup if you want to move your notes somewhere more sync-friendly.

Notes have a 14-digit timestamp ID (like 20260407164313) and a slug derived from the title. The ID is forever; the title can change without breaking anything that links to the note.

To create a note: click New note at the top of the sidebar, or press ⌘N. Give it a title and a body in Markdown.

To edit a note: open it and click Edit in the bar above it, or press ⌘E.

Saving. Zetteling saves the note you're editing a moment after you stop typing, and again when you click Done or go to another page; the label next to Editing shows “Saving…” and “Saved”. A new note is saved for the first time once it has a title and you've moved on from the title field, so its filename uses the whole title. Related notes update when you leave the note or press ⌘S, not while you type, so a cloud AI provider isn't called on every pause. If you'd rather save only when you press Save, turn off Save automatically under Settings → Writing; the button then reads Cancel and discards your changes.

To delete a note: open it and click the bin icon in the bar above it. See Deleting & trash below for what actually happens.

Kinds — four streams for different purposes

Zetteling organizes notes along a kind axis with four values: research, journal, teaching, and life. Every note belongs to exactly one kind. Research is the default; existing notes created before v3.14 are treated as research automatically.

The kinds are streams for different purposes, not workflow stages. Nothing processes a note from one kind to another — a journal entry doesn't graduate into a research note, they're categorically different. The point is to keep journal entries out of your research indexes without forcing you to run a separate app.

  • Research notes use the full Zettelkasten machinery: tags, threads (folgezettel chains), bibliographic refs, wikilinks, backlinks, semantic related-notes. The thread fieldset on the new-note form is only shown for research notes because folgezettel sequences don't apply to daily-journal entries or teaching plans.
  • Journal entries are for day-level journaling — interstitial notes through a day, end-of-day reflections, or anything else date-anchored. The journal index has a new entry button that creates a fresh journal note each time you click it, titled with the current date and time. Click it as often as you have discrete moments worth recording; each click is a clean slate.
  • Teaching notes are for syllabi, lecture plans, student-facing materials, course reflections. You can still use refs (to cite assigned readings) and tags (per course or topic). Threads are available if you need them, but default-hidden on new notes.
  • Life notes are for everything else — academic-life reflections, administrative notes, personal observations, correspondence drafts. Lightweight by default, no required structure.

The navigation bar at the top lets you jump to each kind's filtered index. The index page also has tab controls so you can switch kinds without leaving the page, including an all view that shows everything mixed. In the all view, and in cross-kind contexts like the semantic related-notes panel or backlinks, each note is prefixed with a small colored dot indicating its kind so you can tell at a glance which stream it came from.

Cross-kind links work freely. A research note can link to a teaching note can link to a journal entry via wikilinks. Backlinks span kinds. Full-text search spans kinds. Semantic find-related-notes spans kinds — one of the most valuable use cases is a research note surfacing a journal entry from six months ago that turned out to be related. The kinds segregate the indexes, not the corpus.

You can change a note's kind later by editing it — the kind selector appears at the top of the edit form, and changing it updates the frontmatter on save.

Connecting notes: wikilinks, tags, threads

Wikilinks

To link from one note to another, type the destination's 14-digit ID in double square brackets:

This idea builds on [[20260407164313]] and extends it.

The link will render as the destination note's title. To use custom link text instead, add a pipe and your alias:

This builds on [[20260407164313|my earlier dissonance argument]].

If the destination ID does not exist, the link renders in a dashed grey style — useful for marking "I want to write this note someday." Once you create a note with that ID, the link becomes live automatically.

Backlinks happen for free. Every note's view page shows a Backlinks panel listing every other note that links to it. There is no manual backlink management.

Tags

Add tags in the edit form as a comma-separated list. They become clickable chips on the note view, link to a tag page listing every note carrying that tag, and appear in the master index at tags.

Tag names should be lowercase, hyphenated, and consistent — sts-theory, not STS Theory. The system does not enforce this; it is a discipline thing.

Threads (folgezettel sequences)

A thread is a named sequence of notes linked by prev/next pointers — useful when you are working out an argument across multiple atomic notes and want to walk through them in order. Unlike tags, a single note can be a member of multiple threads simultaneously. Unlike wikilinks, threads impose a sequence rather than a graph.

Threads are configured from two places in the UI. On the new-note form, the thread fieldset lets you either start a new thread with this note as the first entry, or add this note to an existing thread as its new tail — the prev/next pointers are written for you. You can also visit /threads to see every thread in your corpus and create a new thread from there. On any individual note page, a strip at the top shows the note's prev/next neighbors within each thread it belongs to.

Thread configuration is written into the note's YAML frontmatter when you save — if you ever need to untangle or edit a thread manually, you can do so by editing the frontmatter directly in any text editor, but for day-to-day use the UI handles it.

Search

The search box on the home page does a full-text search across the title, body, and tags of every note, with snippet highlighting and ranked results. It uses SQLite's FTS5 engine, which means you can use search operators:

  • drone — matches notes containing "drone"
  • drone NOT military — drone, but exclude any with "military"
  • drone OR uav — either word
  • "civilian drone" — exact phrase
  • drone* — prefix match (drone, drones, droning)

Search is case-insensitive and uses Porter stemming, so orienting, oriented, and orientation all match a search for orient.

Citations and Zotero integration

If you have a bibliography configured, you can reference works in any note using Pandoc-style citekeys:

Building on @aneesh2009 and @browne2015, we can see...

While editing, type @ and a picker pops up in the bottom right of the screen. Type to filter by citekey, title, or author; arrow keys to navigate; Enter to insert. In the rendered note, citekeys become links that jump to the citekeys reference page with that entry anchored, and carry hover tooltips showing author, year, and title.

Setting up the bibliography. In Zotero, install the Better BibTeX extension if you haven't already. Then go to File → Export Library, pick Better BibTeX as the format (not the built-in BibTeX), and in the export options tick the "Keep updated" checkbox before clicking OK. This is the auto-export feature — without it, the .bib file is a one-time snapshot that goes stale the moment you add a new paper. Save the file somewhere stable like ~/Documents/Zotero/library.bib; avoid Downloads since that folder gets cleaned out periodically. Then open the settings page and paste the full path into the bibliography path field. Save. The server picks up the file immediately and watches it for changes — every time Zotero rewrites the export (which now happens automatically, within seconds of any edit to your library), Zetteling re-indexes.

To confirm auto-export is genuinely active rather than just configured, in Zotero go to Settings → Better BibTeX → Auto-export. Your .bib file should appear in the list with a "completed" or "ok" status. After that, you never need to manually re-export — new papers in Zotero appear in Zetteling's @citekey autocomplete within seconds.

Important: use the Better BibTeX export format, not the built-in "BibTeX" format. Zotero ships with two exporters whose names are easy to confuse — the built-in BibTeX and the Better BibTeX format added by the extension. The built-in exporter can produce .bib files without citekeys on each entry, which Zetteling cannot index (every entry needs a citekey like @aneesh2009). Better BibTeX always generates citekeys from your configured template. If you set up the integration and the citekeys page shows zero entries despite a valid path, the most likely cause is that the export was run with the wrong format — re-export using Better BibTeX and the count should match your library.

AI features

Zetteling has four AI-powered features, all of them opt-in and all of them off by default. Nothing in this section runs unless you have explicitly configured a provider in settings. With no provider configured, the AI subsystem stays dormant: the related-notes panel is hidden from note views, the Interrogate button does nothing, the Suggest tags button errors out cleanly. You can use Zetteling for years without ever turning any of this on, and many people should.

If you do want to use the AI features, the rest of this section walks through what each one does, what data it sends where, and how to choose between providers. The privacy page has the complete byte-by-byte account of what gets transmitted; this section is the user-facing version focused on how to use the features rather than what they leak.

Configuring a provider

Open the settings page. There are two independent provider slots: one for chat (used by note interrogation, tag suggestions, and the test-connection button) and one for embeddings (used by semantic related-notes only). They are independent on purpose — the most privacy-conscious configuration is Ollama for embeddings (which run constantly, on every note save) and a cloud provider for chat (which only runs when you click a button).

The four supported chat providers are Anthropic (Claude), OpenAI-compatible (OpenAI itself, OpenRouter, Together, Groq, DeepSeek, and any other provider speaking the OpenAI Chat Completions protocol), Google Gemini, and Ollama (local models on your own hardware). The four supported embedding providers are OpenAI-compatible, Gemini, Ollama, and Voyage AI. Anthropic is chat-only — they do not currently offer first-party embedding models.

For each provider you configure, you supply an API key (except Ollama, which has no key) and optionally a base URL and model name. Defaults are filled in: claude-haiku-5-5 for Anthropic, gpt-5.4-mini for OpenAI, gemini-flash-latest and gemini-embedding-2 for Gemini, qwen2.5:14b for Ollama chat, nomic-embed-text for Ollama embeddings, voyage-3.5 for Voyage. You can override any of these with whichever model you prefer.

Two configuration footguns worth avoiding. First, the chat and embedding slots require different kinds of model. A chat model (qwen2.5:14b, llama3.1, claude-haiku-5-5) cannot produce embeddings; an embedding model (nomic-embed-text, text-embedding-3-small) cannot hold a conversation. If you put a chat model name in the embedding slot, the app will accept the configuration and fail opaquely at every note save. When configuring Ollama specifically, check both model names match the slot they're in. Second, Ollama model names must be ones you've actually pulled with ollama pull <name> — the app cannot download models for you. If a model name in settings doesn't match any locally-installed model, requests will fail with "model not found" errors.

After setting a provider, save, then click Test connection to verify the credentials work. The test sends a minimal "say hello" request to the configured endpoint and reports success or a specific error. No note content is involved in the test.

Semantic find-related-notes

If you've configured an embedding provider, every note's side panel shows a Related list with the most similar notes in your corpus, closest first. The app deliberately shows the order but not the distance numbers, for the reasons in caveats 3 and 4 below. This is the only AI feature that runs automatically — every note save triggers an embedding request when an embed provider is configured, with no per-request button click. If you create or edit 50 notes in a session, that's 50 embedding requests.

Each note gets embedded into a vector when you create or save it (best-effort — if the embedding call fails, the note still saves cleanly and you can backfill later via the reindex button in settings). The vectors are stored in the same SQLite database as the search index, and the Related list compares them (cosine similarity, computed with numpy) each time you open a note.

Four honest caveats to read these results well:

  1. Quality depends entirely on the embedding model. The default Ollama embedding model (nomic-embed-text) is decent but not state-of-the-art. OpenAI's text-embedding-3-small is meaningfully better. text-embedding-3-large is better still but more expensive. Google's gemini-embedding-2 is the current Gemini option (its older text-embedding-004 was shut down in January 2026). If your first try with one model feels weak, switch in the settings page and click Reindex all notes — the embeddings will be recomputed against the new model and the related-notes results will change accordingly.
  2. The most useful results are usually the surprising ones. When you write a note about algorithmic dissonance and the panel surfaces a six-month-old note about algocracy that you'd forgotten existed, that's the system working as designed. When it surfaces three other notes from the same week that you obviously already remember, that's noise. Read the related notes as suggestions to investigate, not as a ranked truth — the value is in the unexpected ones.
  3. Distances are not normalized across models. A distance of 0.4 means something very different in nomic-embed-text than in text-embedding-3-small. Don't try to compare distances across reindexes with different models. The relative ranking within a single corpus on a single model is what matters — which note is closer than which other note — not the absolute numbers.
  4. Cosine similarity itself is not as principled as it looks. Steck, Ekanadham, and Kallus (WWW '24) showed that cosine similarities computed over learned embeddings can, under standard regularization regimes, be made arbitrary by mathematically valid rescalings of the embedding dimensions — meaning the same underlying model can produce wildly different "similarity" rankings depending on training choices that are invisible to you as an end user. The result is derived for regularized linear matrix-factorization models and the authors discuss why analogous concerns extend to deep models trained with combinations of regularizers. The practical takeaway for Zetteling: treat the related-notes ranking as a heuristic for surfacing forgotten neighbors, not as a measurement of conceptual proximity. The numbers are doing less work than they appear to. See: Harald Steck, Chaitanya Ekanadham, and Nathan Kallus, "Is Cosine-Similarity of Embeddings Really About Similarity?", Companion Proceedings of the ACM Web Conference 2024, doi:10.1145/3589335.3651526 (open-access preprint at arxiv.org/abs/2403.05440).

If you ever need to start fresh (you switched models, you imported a lot of new notes, or the index seems out of sync), use the Reindex all notes button on the settings page. It runs in the background with live progress and you can keep working while it happens.

Note interrogation (Interrogate)

On any note, if a chat provider is configured, the side panel has an Interrogate tab (or press ⌘I). It opens a chat scoped to that note: every message you send includes the full note text plus your conversation history so far, and the model responds with that context. Use it for Socratic prompts ("what does this assume?", "what would refute this?", "what's the strongest objection?") or for clarification ("what did I mean by X?", "rewrite this paragraph in plainer terms") — the value is in being prompted to think about the note rather than in trusting the model's claims.

The conversation lives in a Python dictionary in the running app's memory. It is never written to disk, never logged, and is lost whenever the app is closed. Every launch starts with empty conversations. There is no way to recover a previous interrogation session — if a particular exchange was useful, copy the parts you want into a new note manually.

For sensitive material — IRB-protected interview transcripts, unpublished work, anything you would not paste into a cloud service's web UI — configure Ollama as your chat provider before using Interrogate. Ollama runs the model on your own hardware and the request never leaves 127.0.0.1. A 7B to 14B parameter model on modern Apple Silicon is competent enough for Socratic prompting, even if it's not as sharp as Claude or GPT-4 for general chat.

Tag suggestions

In the editor's side panel there is a Suggest tags button; it works once a chat provider is configured and you have at least one tag somewhere in your corpus. Clicking it sends your note's title, the first 4,000 characters of its body, and your full existing tag vocabulary to the chat provider, and asks the model to recommend 3 to 5 tags from the existing list. The response is filtered against your vocabulary set after it returns, so the model cannot invent new tags — anything that doesn't match an existing tag is silently dropped.

This is a deliberate design choice. The point of tags in a Zettelkasten is consistent cross-cutting vocabulary; an AI that invents new tags every time would defeat that. Suggest tags is useful when you've forgotten which existing tag fits a new note, not for tag discovery.

Two practical notes. First, the body is capped at 4,000 characters before being sent — very long notes get truncated, which is fine for tag suggestion (the early body is usually enough to characterize the note's content) but worth knowing. Second, the request only fires when you click the button; nothing is automatic.

Choosing between providers

If you care about privacy above all, use Ollama for everything. Nothing leaves your machine, ever. The cost is speed and quality: local models are smaller and slower than top-tier cloud models. A Mac Mini M4 can run qwen2.5:14b for chat and nomic-embed-text for embeddings comfortably; a base M1 will struggle with anything above 7B.

If you want the best chat quality and don't mind sending note text to a third party, Anthropic Claude is the recommended chat provider. Anthropic does not train on API inputs by default (verify this on their current policy page), and claude-haiku-5-5 is fast and inexpensive enough for casual interrogation use.

For embeddings specifically, OpenAI's text-embedding-3-small is the best price-to-quality ratio among cloud options and a meaningful step up from local models. Voyage AI is competitive and worth trying if you're already paying for it. Gemini's gemini-embedding-2 is fine. If you mix providers — for example, Anthropic for chat and OpenAI for embeddings — you'll need API keys for both. Remember the chat-vs-embedding model distinction from Configuring a provider above: every provider has different model names for each slot, and mixing them up silently breaks the feature.

Avoid the OpenAI-compatible aggregators (OpenRouter, Together, Groq, DeepSeek) for sensitive material unless you have read each provider's data retention policy carefully. The convenience of a single API protocol comes at the cost of policy heterogeneity, and some of these providers train on or retain inputs by default.

Trust model and HTML sanitization

Zetteling assumes by default that you wrote every note in your corpus. Markdown rendering, AI calls, search indexing, and export all treat notes as content you produced and therefore trust. For a single-user local install — which is what most people running Zetteling have — this assumption is correct, and the simplicity it buys is worth more than the hardening it skips.

The assumption breaks the moment you bring in notes you did not write. The most common ways this happens are: importing markdown from someone else (a colleague's research notes, an old Evernote or Notion export), syncing a shared notes folder with a collaborator via Syncthing, or — in the future, if you ever build it — publishing notes to a public site. In each of those cases, an untrusted note could contain HTML or JavaScript that runs in your browser when you view it, which could in turn use Zetteling's own routes to read, modify, or delete other notes.

The mitigation is a single setting: sanitize_note_html on the settings page. Toggle it on and Zetteling runs every rendered note through bleach, which strips dangerous HTML tags and attributes (<script>, <iframe>, onclick=, and so on) while leaving safe markdown intact. The cost is a small loss of expressiveness — if you actually wanted raw HTML in a note, sanitization will eat it — but for any corpus that contains imported content, the tradeoff is correct.

There are several other situations where the default trust assumption breaks in less obvious ways: exposing Zetteling remotely behind a reverse proxy, running Pandoc export on untrusted notes (Pandoc can execute raw LaTeX), feeding untrusted notes through the AI Interrogate feature (prompt injection risk). The full list, with the specific failure mode and mitigation for each, lives in the trust model section of the privacy page. If you're doing anything beyond "single user, my own notes, on my own machine," read it.

The design philosophy is that the default state should be simple and the hardening should be explicit and opt-in, rather than defending against adversaries you do not have. This section exists so the moment you do have them, you know what to change.

Editing notes outside the web UI

This is the whole point of the plain-Markdown design: nothing locks you in. Open your notes folder in Finder, edit any .md file in any editor — Obsidian, VS Code, vim, TextEdit, whatever — and save. The watcher picks up the change within a second or two and the index updates. The web UI will show your changes on the next page reload.

Two practical notes. First, the watcher only looks at the top level of your notes folder — do not put files in subdirectories. If you want to organize your notes spatially, use tags and threads rather than folders. Second, if you rename a file's 14-digit ID prefix, you have effectively created a new note and orphaned all wikilinks pointing at the old ID. Don't do that. Edit the title, the body, the tags freely; leave the ID alone.

Locked notes

A locked note’s text is encrypted on disk. Open its file in Finder, TextEdit, another Markdown app, a backup or a sync service, and the text reads as a block of random characters. Without your password or recovery key, nobody can read it, including you.

Using locked notes

  • Set up once. In Settings → Locked notes, choose a password of at least 10 characters (four or five unrelated words work well). You then get a recovery key, shown once. Print it or keep it in a password manager: if you forget your password, it is the only way back in.
  • Lock a note with the padlock button above it, or ⌘K → “Lock this note”.
  • Lock a whole kind. Under Always lock these kinds, tick a kind (Journal, say). Its existing notes are locked straight away, and new notes of that kind are created locked. A note you move into a ticked kind is locked when you save it.
  • Opening them. The first time you open a locked note, Zetteling asks for your password. Locked notes then stay open until you quit, or until Zetteling has been idle for the time you choose (5, 15, 30 or 60 minutes, or only on quit). If they close while you’re editing, what you’ve typed is saved first; if it can’t be, the editor asks for the password before saving. ⌘K → “Lock notes now” closes them at once.
  • Removing a lock (the open-padlock button on a locked note) turns it back into a plain Markdown file. Remove all locks in Settings does this for every locked note.
  • Changing your password doesn’t change the encrypted text, so it’s quick, and your recovery key keeps working. Forgot it? Use Use recovery key in Settings, or the link on the unlock screen, to set a new one.

What stays readable

By design, only the text is encrypted. A locked note’s title, tags, kind, thread names and order, created and modified dates, ID and filename (which includes the title) stay in plain text, so your note list, threads and title search keep working. The size of the encrypted block also gives away roughly how long the note is.

What locked notes don’t do

  • No AI. A locked note is never sent to an AI provider: Interrogate, tag suggestions and related notes are off for it, and any related-notes data made before you locked it is deleted.
  • Search finds titles and tags, not text. A locked note’s text is kept out of the search index, even while it’s open, and the text indexed before you locked it is erased from the index.
  • Links inside a locked note don’t show up as backlinks on the notes they point to.
  • Exports are not encrypted. Exporting a locked note produces an ordinary Word, LaTeX or HTML file, and the export page says so.
  • Earlier copies stay as they were. Locking a note doesn’t reach copies made before: Time Machine, version history in iCloud Drive or Dropbox, Git history, or earlier exports. If those matter, delete them there. The disk itself may also keep old blocks of the file until they’re reused; FileVault, which encrypts the whole disk, covers that.
  • While open, the text is in memory. Anything that can read Zetteling’s memory on your Mac could read open notes. Python can’t promise to wipe memory, so quitting is the surest way to close them.

The encryption, in detail

Locked notes use standard, widely reviewed building blocks, the current recommendations for each job:

Tampering. GCM’s authentication tag detects any change to the encrypted text. A locked note that has been altered or damaged won’t open; Zetteling says so rather than showing corrupted text.

Where the keys are. The wrapped keys and Argon2id settings (never your password or the data key) are kept in .zetteling-vault.json in your notes folder, and a copy travels inside every locked note, so a note can still be opened with your password if that file goes missing. Back up your whole notes folder, hidden files included (in Finder, ⇧⌘. shows them).

What a locked file looks like. The usual frontmatter, with locked: true, followed by a block between -----BEGIN ZETTELING LOCKED NOTE----- and -----END ZETTELING LOCKED NOTE-----.

Limits. The scheme combines standard parts in a standard way, but Zetteling’s use of them hasn’t been independently audited. If your work needs certified encryption (some ethics protocols and data-protection rules require it), check with your institution, and consider an encrypted disk image or FileVault as well.

Deleting and the trash

The delete button moves the note's file into a .trash subdirectory of your notes folder with a timestamp suffix appended to the filename. The note disappears from the index immediately. The file itself is still on your disk, recoverable.

To restore a deleted note: open the trash folder in Finder, find the file (filenames look like 20260407164313-mynote.md.20260407164314.deleted), drag it back into your notes folder, and rename it to remove the .20260407164314.deleted suffix so it ends in .md again. The watcher will pick it up.

To permanently delete: empty the trash folder in Finder yourself. The app will never do this for you.

Exporting to Word, LaTeX, HTML, and other formats

The Zettelkasten is not just a thinking tool — it is also the upstream of your actual writing output. Any single note, any thread, or any group of notes sharing a tag can be exported to a finished document via Pandoc.

Pandoc is bundled. Zetteling ships with a copy of Pandoc inside the app bundle, so the export features work out of the box on the packaged desktop app — no separate install required. If exports silently fail or produce nothing, see the killed: 9 entry under Troubleshooting.

Three export sources, accessible from three places:

  • From any note, click the export icon in the bar above it — exports just that note.
  • From a thread page (e.g. /thread/dissonance-arc), click export this thread in the header — exports the full chain in order, with each note as a section of the resulting document.
  • From a tag page (e.g. /tag/sts-theory), click export all — exports every note carrying that tag.

The export form lets you pick the output format (Word, LaTeX, HTML, EPUB, ODT, plain text, or pure Markdown) and toggle whether @citekey references should be processed by pandoc-citeproc using your configured BibTeX file (which produces formatted citations and an automatically-generated references section). The result downloads as a file you can open in Word, edit further, and turn into a paper.

For PDF output, the easiest path is to export to HTML or Word and use your browser or word processor's print-to-PDF feature. Direct PDF export from Pandoc requires a LaTeX engine (XeLaTeX, pdfLaTeX, etc.) which is not bundled with Zetteling — install MacTeX or TeX Live separately if you want this. For most writing workflows, Word export plus the word processor's native PDF export is simpler and produces better-looking output than direct Pandoc-to-PDF anyway.

Writing stats

The stats page shows total notes, total words, mean and median words per note, a 30-day notes-per-day sparkline, an hour-of-day distribution of when you write, your most-linked notes, and your top tags.

It is deliberately observation-only. There are no streaks, no daily targets, no "you didn't write today" notifications. Stats here are a way to see your work as a body across time, not a way to discipline yourself. Some weeks you will write a lot of notes; some weeks you will spend reading and thinking and write nothing. Both are correct. The stats page reflects this without judgment.

Settings, themes, and the About pages

The settings page (at the bottom of the sidebar, or ⌘,) is where Zetteling's configurable behavior lives. There is no command-line flag, no config file you have to edit by hand for normal use — everything is a form field. The settings persist to a settings.json file next to the database in the app's data folder, and changes take effect immediately on save, except for the notes directory which requires a restart.

The main things you can configure: AI providers and models (chat and embedding slots, with API keys, base URLs, and model names — see AI features above); the notes directory (where your .md files live on disk — see Sync & backup for migration guidance); the bibliography path for the Zotero/Pandoc integration (see Citations); the HTML sanitization toggle (see Trust model); and a few smaller knobs you can discover by visiting the page.

Themes and appearance. Settings → Appearance lets you choose a light theme (Meadow, Lagoon, Blossom or Paper), a dark theme (Starlit, Forest or Midnight), whether the app follows your Mac between them, an accent colour, the interface font, the reading and writing font, the text size, and whether the background illustrations are shown. Changes apply straight away and are saved in settings.json. The moon or sun button at the bottom of the sidebar cycles quickly between match my Mac, always light and always dark.

About, privacy and licence. The last section of the settings page links to What's new (the version history), Privacy (the complete account of what data goes where) and the Licence (PolyForm Noncommercial 1.0.0: free for noncommercial use; see the page for the full terms). The palette finds them too: ⌘K → “About”.

Sync and backup

Your corpus is a folder full of plain text files. Every backup tool ever invented works on it: Time Machine, rsync, Git, Dropbox, iCloud Drive, Syncthing. The simplest possible approach — let Time Machine or your existing cloud backup handle it — is entirely sufficient for most users. The rest of this section covers the slightly more involved options for people who want version history or multi-device sync.

Migrating your notes to a sync-friendly location

The default notes location is inside Zetteling's application-data folder — typically ~/Library/Application Support/com.shivissar.zetteling/notes/ on macOS. That's fine for Time Machine but awkward for file-sync tools like Syncthing or Dropbox, which tend to refuse hidden system paths. If you want to sync your notes, migrate the folder first.

Zetteling does not move your notes for you when you change the setting — it only updates where it looks for notes on next launch. You have to copy the files yourself before flipping the setting, or you will open Zetteling to an empty corpus and briefly believe you have lost everything. Here is the safe sequence:

  1. Decide where you want your notes to live. Good options include ~/Documents/Zetteling/notes, ~/Zetteling/notes, or ~/notes — anywhere your sync tool can reach without permission contortions. Create the parent directory if needed.
  2. Quit Zetteling completely.
  3. In Finder or a terminal, copy the entire contents of your current notes folder (the path shown on the settings page) into your chosen new location. Use copy, not move, so you have a fallback if anything goes wrong.
  4. Launch Zetteling again. Open the settings page, set the notes directory field to your new path, and save. The page will tell you the change won't take effect until restart.
  5. Quit and relaunch Zetteling.
  6. Verify your notes are all visible — the count on the home page should match what you had before.
  7. Once you have confirmed everything is in the new location and Zetteling is reading from it correctly, you can delete the original copy in the application-data folder. Don't delete it on the same day you migrate. Wait a week.

Git for version history

From inside your notes folder, run:

git init
git add .
git commit -m "initial commit"

Then commit periodically — daily, weekly, whatever rhythm you like. You get free undo for everything you've ever written. To see the history of any single note:

git log -p 20260407164313-mynote.md

This is independent of the soft-delete trash and works even if the whole notes folder gets accidentally destroyed. For convenience, you can wire up a cron job or a launchd plist to auto-commit nightly.

Syncthing for multi-device access

Optional and worth skipping if you only use one machine. Syncthing is a free, open source, end-to-end encrypted, peer-to-peer file sync tool. It mirrors a folder between two or more devices without any central server. The architecture of Zetteling is local-first: each device runs its own copy of the app pointing at its own copy of the notes folder, and Syncthing keeps the notes folders in agreement.

Critical rule: sync only your notes folder. Never sync the application-data folder containing zettel.db and settings.json — the database is per-machine and rebuilds itself from the notes; sharing it across devices would corrupt it. The settings file contains API keys and machine-specific preferences. Sync the notes folder only, nothing else.

Step 1 — Install on your Mac:

brew install syncthing
brew services start syncthing

Open http://127.0.0.1:8384 in any browser. You should see the Syncthing GUI. This is your local Syncthing's control panel.

Step 2 — Install on your second device. For another Mac, use the same brew commands. For a Linux machine (e.g. a VPS or home server), install via your distribution's package manager and enable the user service:

sudo apt install -y syncthing
sudo loginctl enable-linger $USER
systemctl --user enable syncthing.service
systemctl --user start syncthing.service

The enable-linger command lets the service keep running after you log out of SSH. The Syncthing GUI on a remote machine listens on localhost only for security; to access it from your Mac, open an SSH tunnel:

ssh -L 8384:127.0.0.1:8384 your_user@your.server.example.com

While that SSH session is open, visit http://127.0.0.1:8384 on your Mac — you're now talking to the remote Syncthing GUI through the tunnel. If your Mac's own Syncthing is also using port 8384, use a different local port (ssh -L 8385:127.0.0.1:8384 ... and visit :8385).

Step 3 — Pair the devices. Each Syncthing instance has a unique Device ID (a long string like A1B2C3D-...).

  • On the first Mac's GUI: click Actions, Show ID and copy the device ID.
  • On the second device's GUI: click Add Remote Device, paste the first Mac's ID, give it a name, and save.
  • Back on the first Mac's GUI: a notification appears asking whether to add the other device as a remote. Accept it.

Step 4 — Share the notes folder:

  • On the first Mac's GUI: click Add Folder. Set Folder Path to the absolute path of your Zetteling notes directory. Give it a label like "zetteling-notes". In the Sharing tab, tick the box next to your other device. In the File Versioning tab, choose Staggered File Versioning with default settings. Save.
  • On the other device's GUI: a notification appears asking whether to accept the new folder share. Click Add, then set the folder path to wherever you want Zetteling's notes to live on that machine. Save.

Within a minute, every .md file from your first Mac will appear on the other device, and the watcher on each side will pick up changes automatically. Conflict files (if two devices edit the same note simultaneously) are saved as .sync-conflict-... files alongside the original — nothing is ever silently lost.

Optional: sync your bibliography too. If you use the Zotero/BibTeX integration, put the .bib file inside the same Syncthing folder so it travels with your notes.

Troubleshooting

I edited a file in vim/Obsidian and the web UI doesn't show my changes
Reload the page. The watcher updates the index in the background but the page itself doesn't auto-refresh. If a reload doesn't show the change, check that you saved the file directly inside your notes directory (the path shown on the settings page) and not in a subdirectory.
Exports silently fail or produce nothing, possibly with killed: 9 in the logs
The bundled Pandoc binary has macOS quarantine attributes that need to be stripped after the app is installed. Open Terminal and run xattr -cr /Applications/Zetteling.app. Then retry the export. This is a one-time fix per install; subsequent launches don't require it.
Bibliography shows zero entries despite a configured path
The most common cause is that your .bib file was exported from Zotero using the built-in BibTeX format rather than the Better BibTeX format. The built-in exporter can produce entries without citekeys, which Zetteling cannot index. In Zotero, re-export your library using Better BibTeX (added by the Better BibTeX extension), save to a new file, and point the settings page at the new file. The count on the citekeys page should match your library.
I added a new paper to Zotero and it doesn't appear in Zetteling's autocomplete
Your Better BibTeX export is probably a one-time snapshot rather than an auto-export. A static .bib file goes stale the moment you add or edit anything in Zotero. To fix this, in Zotero go to Settings → Better BibTeX → Auto-export and check whether your .bib file is listed there. If it isn't, re-create the export with the "Keep updated" checkbox ticked — see Citations above for the full setup. Once auto-export is active, the .bib file regenerates within seconds of any Zotero edit, and Zetteling re-indexes automatically.
Search returns no results for words I know are in my notes
The index may be out of sync. Quit Zetteling completely, delete the database file zettel.db (it lives in the application-data folder; the exact path is shown at the top of the settings page next to notes directory), and relaunch. The watcher does a full reconciliation on startup and rebuilds the index from your notes folder. This is always safe — the database is disposable and contains nothing your notes don't.
A wikilink shows as broken even though the note exists
The link must use the destination note's exact 14-digit ID, not its title or filename. Find the destination note, look at its URL or the small id shown under its title, and use that exact number.
The citation picker doesn't appear when I type @
You don't have a bibliography configured. Open the settings page and set the bibliography path field to point at your .bib file. See Citations above for the full setup walkthrough, including the Better BibTeX format requirement.
AI features show "no provider configured" or just don't appear
You haven't set up an AI provider. Open the settings page, pick a chat provider and/or an embeddings provider from the dropdowns, supply an API key (or leave it blank for Ollama), and click Test to verify. Until at least one provider is configured, the Interrogate button, the Suggest tags button, and the related-notes panel all stay dormant.
Ollama errors with "connection refused" or "is the Ollama server running?"
Ollama is configured but its server isn't running. In a terminal, run ollama serve and leave it running, then retry the AI feature. If ollama serve isn't installed, install Ollama from ollama.com first. If the server is running but Zetteling still can't reach it, check the base URL on the settings page — it should be http://127.0.0.1:11434 for a local install.
Ollama errors with "model not found" or "try pulling"
The model name you configured doesn't match anything you've downloaded. In a terminal, run ollama list to see what's actually available, then either change the model name on the settings page to match one of those, or run ollama pull <model-name> to download the one you want. Common gotcha: configuring a chat model (like qwen2.5:14b or llama3.1) in the embeddings slot, or vice versa. Embeddings need a dedicated embedding model like nomic-embed-text; using a chat model as an embedding model will fail opaquely.
I want to start completely fresh
Quit Zetteling. Delete zettel.db from the application-data folder (path shown on the settings page) and, if you want a truly empty corpus, move your notes folder aside. Relaunch. You'll get an empty Zettelkasten that rebuilds itself from whatever notes remain.
Something is broken in a way not covered here
As a first move, quit and relaunch Zetteling — many transient problems (file watcher hiccups, stale connections) clear up. For the packaged desktop app, BeeWare logs are written to the application-data folder and can be viewed with Console.app or log stream --predicate 'process == "Zetteling"' in Terminal.
