What is a Zettelkasten?

A Zettelkasten ("slip box" in German) is a note-taking method developed by the German sociologist Niklas Luhmann, who used it across forty years of work to produce around seventy books and four hundred peer-reviewed papers. His Zettelkasten contained roughly 90,000 paper slips. When asked how he was so prolific, Luhmann famously replied that he wasn't — his Zettelkasten was.

The method has four central principles, all of which this app is built around:

1. Atomic notes. Each note expresses one idea, one observation, or one argument — not a topic, not a chapter, not a meeting summary. The unit is the smallest thing that can stand on its own. A note titled "Algorithmic governance erodes accountability" is atomic; a note titled "Notes on Aneesh's chapter 3" is not. The reason for atomicity is that small ideas combine and recombine in ways that large ones cannot — an atomic note about dissonance can show up unexpectedly in arguments about labor, surveillance, or affect, whereas a chapter summary can only be cited as itself.

2. Links between notes are the structure. A Zettelkasten has no folder hierarchy. Notes are connected to each other by direct references — in this app, that's the [[id]] wikilink syntax. Over time the web of links becomes the structure: it grows organically from your actual thinking rather than from a category scheme you imposed in advance. The backlinks panel on every note shows what other notes have referenced it, which is how new connections surface.

3. Notes are written in your own words. A Zettelkasten is not a quote collection. The act of rewriting an idea in your own words, in your own voice, is the moment of understanding. If you copy a passage verbatim, you have moved text from one place to another but you have not yet thought about it. Sönke Ahrens makes this argument forcefully in How to Take Smart Notes (2017): the friction of rewriting is the cognitive work, and shortcuts that bypass it (including AI-generated summaries) defeat the epistemic point of the method.

4. The system serves long-term writing, not retrieval. A Zettelkasten is not a search engine for your past readings — for that you have Google Scholar and Zotero. It is a thinking partner across years. You write notes today not because you need them today, but because some future project will surprise you by drawing on them. This is why the method rewards consistency more than volume.

How this app maps onto the method. Wikilinks [[id]] are how you connect notes; backlinks (shown automatically on every note view) are how connections surface in reverse. Tags are a lightweight grouping mechanism for cross-cutting themes that don't deserve their own thread. Threads are this app's implementation of Luhmann's Folgezettel — sequential chains where notes follow each other in a deliberate argumentative order, and a single note can belong to multiple threads simultaneously. The citation system lets you reference Zotero entries by @citekey without copying their text — your notes stay in your voice, while pointing precisely at the sources behind your claims.

For deeper reading: Sönke Ahrens, How to Take Smart Notes (2nd ed., 2022); Luhmann's own brief essay Communicating with Slip Boxes (1981, translated by Manfred Kuehn); and the writing of Andy Matuschak on evergreen notes at notes.andymatuschak.org.

The basics

Every note is a single plain Markdown file in your notes/ folder. Zetteling is packaged as a desktop application via BeeWare — when you launch the .app bundle (or run briefcase dev from source), it starts a local Flask server on an ephemeral port and opens a native window pointing at it. The web interface you are reading right now is one way to interact with those files; any text editor you like is another. The two are kept in sync automatically — edit a file in Obsidian, vim, or TextEdit and the index will update within a second or two.

Notes have a 14-digit timestamp ID (like 20260407164313) and a slug derived from the title. The ID is forever; the title can change without breaking anything that links to the note.

To create a note: click + new in the top right. Give it a title and a body in Markdown. Save.

To edit a note: open it and click edit at the bottom.

To delete a note: open it and click the red delete button. See Deleting & trash below for what actually happens.

Kinds — four streams for different purposes

Zetteling organizes notes along a kind axis with four values: research, journal, teaching, and life. Every note belongs to exactly one kind. Research is the default; existing notes created before v3.14 are treated as research automatically.

The kinds are streams for different purposes, not workflow stages. Nothing processes a note from one kind to another — a journal entry doesn't graduate into a research note, they're categorically different. The point is to keep journal entries out of your research indexes without forcing you to run a separate app.

  • Research notes use the full Zettelkasten machinery: tags, threads (folgezettel chains), bibliographic refs, wikilinks, backlinks, semantic related-notes. The thread fieldset on the new-note form is only shown for research notes because folgezettel sequences don't apply to daily-journal entries or teaching plans.
  • Journal entries are for day-level journaling — interstitial notes through a day, end-of-day reflections, or anything else date-anchored. The journal index has a today's entry button that creates or resumes a journal note titled with today's date (YYYY-MM-DD). Click it once in the morning, fill it in through the day; click it again and you're back in the same note.
  • Teaching notes are for syllabi, lecture plans, student-facing materials, course reflections. You can still use refs (to cite assigned readings) and tags (per course or topic). Threads are available if you need them, but default-hidden on new notes.
  • Life notes are for everything else — academic-life reflections, administrative notes, personal observations, correspondence drafts. Lightweight by default, no required structure.

The navigation bar at the top lets you jump to each kind's filtered index. The index page also has tab controls so you can switch kinds without leaving the page, including an all view that shows everything mixed. In the all view, and in cross-kind contexts like the semantic related-notes panel or backlinks, each note is prefixed with a small colored dot indicating its kind so you can tell at a glance which stream it came from.

Cross-kind links work freely. A research note can link to a teaching note can link to a journal entry via wikilinks. Backlinks span kinds. Full-text search spans kinds. Semantic find-related-notes spans kinds — one of the most valuable use cases is a research note surfacing a journal entry from six months ago that turned out to be related. The kinds segregate the indexes, not the corpus.

You can change a note's kind later by editing it — the kind selector appears at the top of the edit form, and changing it updates the frontmatter on save.

Wikilinks

To link from one note to another, type the destination's 14-digit ID in double square brackets:

This idea builds on [[20260407164313]] and extends it.

The link will render as the destination note's title. To use custom link text instead, add a pipe and your alias:

This builds on [[20260407164313|my earlier dissonance argument]].

If the destination ID does not exist, the link renders in a dashed grey style — useful for marking "I want to write this note someday." Once you create a note with that ID, the link becomes live automatically.

Backlinks happen for free. Every note's view page shows a "Backlinks" panel listing every other note that links to it. There is no manual backlink management.

Tags

Add tags in the edit form as a comma-separated list. They become clickable chips on the note view, link to a tag page listing every note carrying that tag, and appear in the master index at tags.

Tag names should be lowercase, hyphenated, and consistent — sts-theory, not STS Theory. The system does not enforce this; it is a discipline thing.

Threads (folgezettel sequences)

A thread is a named sequence of notes linked by prev/next pointers — useful when you are working out an argument across multiple atomic notes and want to be able to walk through them in order. Unlike tags, a single note can be a member of multiple threads simultaneously. Unlike wikilinks, threads impose a sequence rather than a graph.

Threads are currently configured by editing a note's YAML frontmatter directly. Open notes/your-note.md in any text editor and add a threads: block:

---
id: '20260407164313'
title: Algorithmic dissonance, first move
threads:
  - name: dissonance-arc
    prev: null
    next: '20260407164314'
---

Then on the next note in the sequence:

---
id: '20260407164314'
title: Algorithmic dissonance, second move
threads:
  - name: dissonance-arc
    prev: '20260407164313'
    next: '20260407164315'
---

Save the files. The web UI picks them up immediately. Visit threads to see all configured threads, and click any thread name to walk its chain in order. On any individual note page, you'll see a strip showing its prev/next neighbors within each thread it belongs to.

A graphical thread editor is on the roadmap but deliberately not built yet — I want to see whether the YAML approach is actually painful in real use first.

Search

The search box on the home page does a full-text search across the title, body, and tags of every note, with snippet highlighting and ranked results. It uses SQLite's FTS5 engine, which means you can use search operators:

  • drone — matches notes containing "drone"
  • drone NOT military — drone, but exclude any with "military"
  • drone OR uav — either word
  • "civilian drone" — exact phrase
  • drone* — prefix match (drone, drones, droning)

Search is case-insensitive and uses Porter stemming, so orienting, oriented, and orientation all match a search for orient.

Citations and Zotero integration

If you have a bibliography configured (the cite link in the top nav will list entries; otherwise it shows a setup hint), you can reference works in any note using Pandoc-style citekeys:

Building on @aneesh2009 and @browne2015, we can see…

While editing, type @ and a picker pops up in the bottom right of the screen. Type to filter by citekey, title, or author; arrow keys to navigate; Enter to insert. In the rendered note, citekeys become links with hover tooltips showing author, year, and title.

To set up the bibliography, in Zotero install the Better BibTeX extension, and configure it to auto-export your library to a .bib file at a stable path on disk. Then open the settings page and paste that path into the bibliography path field. Save. The server picks up the file immediately and watches it for changes — every time Zotero rewrites the export, Zetteling re-indexes automatically.

Power users running Zetteling headlessly (e.g. on a VPS via the Flask server directly rather than the desktop app) can override the settings value with the ZETTEL_BIB_PATH environment variable, which takes precedence over whatever is stored in settings.json. For the desktop app, the settings page is the right place.

AI features

Zetteling has four AI-powered features, all of them opt-in and all of them off by default. Nothing in this section runs unless you have explicitly configured a provider in settings. With no provider configured, the AI subsystem stays dormant: the related-notes panel is hidden from note views, the Interrogate button does nothing, the Suggest tags button errors out cleanly. You can use Zetteling for years without ever turning any of this on, and many people should.

If you do want to use the AI features, the rest of this section walks through what each one does, what data it sends where, and how to choose between providers. The privacy page has the complete byte-by-byte account of what gets transmitted; this section is the user-facing version focused on how to use the features rather than what they leak.

Configuring a provider

Open the settings page. There are two independent provider slots: one for chat (used by note interrogation, tag suggestions, and the test-connection button) and one for embeddings (used by semantic related-notes only). They are independent on purpose — the most privacy-conscious configuration is Ollama for embeddings (which run constantly, on every note save) and a cloud provider for chat (which only runs when you click a button).

The four supported chat providers are Anthropic (Claude), OpenAI-compatible (OpenAI itself, OpenRouter, Together, Groq, DeepSeek, and any other provider speaking the OpenAI Chat Completions protocol), Google Gemini, and Ollama (local models on your own hardware). The four supported embedding providers are OpenAI-compatible, Gemini, Ollama, and Voyage AI. Anthropic is chat-only — they do not currently offer first-party embedding models.

For each provider you configure, you supply an API key (except Ollama, which has no key) and optionally a base URL and model name. Defaults are filled in: claude-haiku-4-5 for Anthropic, gpt-4o-mini for OpenAI, qwen2.5:14b for Ollama chat, nomic-embed-text for Ollama embeddings, voyage-3.5 for Voyage. You can override any of these with whichever model you prefer — Zetteling does not constrain the model list, so newer Anthropic, OpenAI, or Gemini models work as soon as you type their name.

After setting a provider, click Test next to the field to verify the credentials work. The test sends a minimal "say hello" request to the configured endpoint and reports success or a specific error. No note content is involved in the test.

Semantic find-related-notes

If you've configured an embedding provider, every note view shows a "Related (semantic)" sidebar with the most conceptually similar notes from your corpus, ranked by cosine distance. Smaller distance = more similar. This is the only AI feature that runs automatically — every note save triggers an embedding request when an embed provider is configured, with no per-request button click. If you create or edit 50 notes in a session, that's 50 embedding requests.

Each note gets embedded into a vector when you create or save it (best-effort — if the embedding call fails, the note still saves cleanly and you can backfill later via the reindex button in settings). The vectors live in a sqlite-vec table in the same database as the search index, and the related-notes panel does a vector nearest-neighbors query on every note view.

Four honest caveats to read these results well:

1. Quality depends entirely on the embedding model. The default Ollama embedding model (nomic-embed-text) is decent but not state-of-the-art. OpenAI's text-embedding-3-small is meaningfully better. text-embedding-3-large is better still but more expensive. Google's text-embedding-004 is competitive. If your first try with one model feels weak, switch in the settings page and click Reindex all notes — the embeddings will be recomputed against the new model and the related-notes results will change accordingly.

2. The most useful results are usually the surprising ones. When you write a note about algorithmic dissonance and the panel surfaces a six-month-old note about algocracy that you'd forgotten existed, that's the system working as designed. When it surfaces three other notes from the same week that you obviously already remember, that's noise. Read the related notes as suggestions to investigate, not as a ranked truth — the value is in the unexpected ones.

3. Distances are not normalized across models. A distance of 0.4 means something very different in nomic-embed-text than in text-embedding-3-small. Don't try to compare distances across reindexes with different models. The relative ranking within a single corpus on a single model is what matters — which note is closer than which other note — not the absolute numbers.

4. Cosine similarity itself is not as principled as it looks. Steck, Ekanadham, and Kallus (WWW '24) showed that cosine similarities computed over learned embeddings can, under standard regularization regimes, be made arbitrary by mathematically valid rescalings of the embedding dimensions — meaning the same underlying model can produce wildly different "similarity" rankings depending on training choices that are invisible to you as an end user. The result is derived for regularized linear matrix-factorization models and the authors discuss why analogous concerns extend to deep models trained with combinations of regularizers. The practical takeaway for Zetteling: treat the related-notes ranking as a heuristic for surfacing forgotten neighbors, not as a measurement of conceptual proximity. The numbers are doing less work than they appear to. See: Harald Steck, Chaitanya Ekanadham, and Nathan Kallus, "Is Cosine-Similarity of Embeddings Really About Similarity?", Companion Proceedings of the ACM Web Conference 2024, doi:10.1145/3589335.3651526 (open-access preprint at arxiv.org/abs/2403.05440).

If you ever need to start fresh (you switched models, you imported a lot of new notes, or the index seems out of sync), use the Reindex all notes button on the settings page. It runs in the background with live progress and you can keep working while it happens.

Note interrogation (Interrogate)

On any note view, if a chat provider is configured, you'll see an Interrogate button. Clicking it opens a chat panel scoped to that note: every message you send includes the full note text plus your conversation history so far, and the model responds with that context. Use it for Socratic prompts ("what does this assume?", "what would refute this?", "what's the strongest objection?") or for clarification ("what did I mean by X?", "rewrite this paragraph in plainer terms") — the value is in being prompted to think about the note rather than in trusting the model's claims.

The conversation lives in a Python dictionary in the running app's memory. It is never written to disk, never logged, and is lost whenever the app is closed. In the desktop build that means every launch starts with empty conversations. There is no way to recover a previous interrogation session — if a particular exchange was useful, copy the parts you want into a new note manually.

For sensitive material — IRB-protected interview transcripts, unpublished work, anything you would not paste into a cloud service's web UI — configure Ollama as your chat provider before using Interrogate. Ollama runs the model on your own hardware and the request never leaves 127.0.0.1. A 7B–14B parameter model on modern Apple Silicon is competent enough for Socratic prompting, even if it's not as sharp as Claude or GPT-4 for general chat.

Tag suggestions

In the note edit form, if a chat provider is configured and you have at least one tag somewhere in your corpus, a Suggest tags button appears. Clicking it sends your note's title, the first 4,000 characters of its body, and your full existing tag vocabulary to the chat provider, and asks the model to recommend 3–5 tags from the existing list. The response is filtered against your vocabulary set after it returns, so the model cannot invent new tags — anything that doesn't match an existing tag is silently dropped.

This is a deliberate design choice. The point of tags in a Zettelkasten is consistent cross-cutting vocabulary; an AI that invents new tags every time would defeat that. Suggest tags is useful when you've forgotten which existing tag fits a new note, not for tag discovery.

Two practical notes. First, the body is capped at 4,000 characters before being sent — very long notes get truncated, which is fine for tag suggestion (the early body is usually enough to characterize the note's content) but worth knowing. Second, the request only fires when you click the button; nothing is automatic.

Choosing between providers

If you care about privacy above all, use Ollama for everything. Nothing leaves your machine, ever. The cost is speed and quality: local models are smaller and slower than top-tier cloud models. A Mac Mini M4 can run qwen2.5:14b for chat and nomic-embed-text for embeddings comfortably; a base M1 will struggle with anything above 7B.

If you want the best chat quality and don't mind sending note text to a third party, Anthropic Claude is the recommended chat provider. Anthropic does not train on API inputs by default (verify this on their current policy page), and claude-haiku-4-5 is fast and inexpensive enough for casual interrogation use.

For embeddings specifically, OpenAI's text-embedding-3-small is the best price-to-quality ratio among cloud options and a meaningful step up from local models. Voyage AI is competitive and worth trying if you're already paying for it. Gemini's text-embedding-004 is fine. If you mix providers — for example, Anthropic for chat and OpenAI for embeddings — you'll need API keys for both.

Avoid the OpenAI-compatible aggregators (OpenRouter, Together, Groq, DeepSeek) for sensitive material unless you have read each provider's data retention policy carefully. The convenience of a single API protocol comes at the cost of policy heterogeneity, and some of these providers train on or retain inputs by default.

Trust model and HTML sanitization

Zetteling assumes by default that you wrote every note in your corpus. Markdown rendering, AI calls, search indexing, and export all treat notes as content you produced and therefore trust. For a single-user local install — which is what most people running Zetteling have — this assumption is correct, and the simplicity it buys is worth more than the hardening it skips.

The assumption breaks the moment you bring in notes you did not write. The most common ways this happens are: importing markdown from someone else (a colleague's research notes, an old Evernote or Notion export), syncing a shared notes folder with a collaborator via Syncthing, or — in the future, if you ever build it — publishing notes to a public site. In each of those cases, an untrusted note could contain HTML or JavaScript that runs in your browser when you view it, which could in turn use Zetteling's own routes to read, modify, or delete other notes.

The mitigation is a single setting: sanitize_note_html on the settings page. Toggle it on and Zetteling runs every rendered note through bleach, which strips dangerous HTML tags and attributes (<script>, <iframe>, onclick=, and so on) while leaving safe markdown intact. The cost is a small loss of expressiveness — if you actually wanted raw HTML in a note, sanitization will eat it — but for any corpus that contains imported content, the tradeoff is correct.

There are several other situations where the default trust assumption breaks in less obvious ways: exposing Zetteling remotely behind a reverse proxy, running Pandoc export on untrusted notes (Pandoc can execute raw LaTeX), feeding untrusted notes through the AI Interrogate feature (prompt injection risk). The full list, with the specific failure mode and mitigation for each, lives in the trust model section of the privacy page. If you're doing anything beyond "single user, my own notes, on my own machine," read it.

The design philosophy is that the default state should be simple and the hardening should be explicit and opt-in, rather than defending against adversaries you do not have. This section exists so the moment you do have them, you know what to change.

Editing notes outside the web UI

This is the whole point of the plain-Markdown design: nothing locks you in. Open the notes/ folder in Finder, edit any .md file in any editor — Obsidian, VS Code, vim, TextEdit, whatever — and save. The watcher picks up the change within a second or two and the index updates. The web UI will show your changes on the next page reload.

Two practical notes. First, do not put files in subdirectories of notes/ — the watcher only looks at the top level. Second, if you rename a file's 14-digit ID prefix, you have effectively created a new note and orphaned all wikilinks pointing at the old ID. Don't do that. Edit the title, the body, the tags freely; leave the ID alone.

Deleting and the trash

The delete button moves the note's file into notes/.trash/ with a timestamp suffix appended to the filename. The note disappears from the index immediately. The file itself is still on your disk, recoverable.

To restore a deleted note: open notes/.trash/ in Finder, find the file (filenames look like 20260407164313-mynote.md.20260407164314.deleted), drag it back into notes/, and rename it to remove the .20260407164314.deleted suffix so it ends in .md again. The watcher will pick it up.

To permanently delete: empty notes/.trash/ in Finder yourself. The app will never do this for you.

Exporting to Word, LaTeX, HTML, and other formats

The Zettelkasten is not just a thinking tool — it is also the upstream of your actual writing output. Any single note, any thread, or any group of notes sharing a tag can be exported to a finished document via Pandoc.

Prerequisite: install Pandoc on your system. On macOS, brew install pandoc; on Ubuntu/Debian, sudo apt install pandoc; on Windows, see pandoc.org/installing. If Pandoc is not installed, the export pages show install instructions instead of the export form.

Three export sources, accessible from three places:

  • From any note's view page, click export in the action row at the bottom — exports just that note.
  • From a thread page (e.g. /thread/dissonance-arc), click export this thread in the header — exports the full chain in order, with each note as a section of the resulting document.
  • From a tag page (e.g. /tag/sts-theory), click export all — exports every note carrying that tag.

The export form lets you pick the output format (Word, LaTeX, HTML, EPUB, ODT, plain text, or pure Markdown) and toggle whether @citekey references should be processed by pandoc-citeproc using your configured BibTeX file (which produces formatted citations and an automatically-generated references section). The result downloads as a file you can open in Word, edit further, and turn into a paper.

For PDF output, the easiest path is to export to HTML or Word and use your browser or word processor's print-to-PDF feature. Direct PDF export from Pandoc requires a LaTeX engine (XeLaTeX, pdfLaTeX, etc.); install MacTeX or TeX Live if you want this.

Writing stats

The stats page shows total notes, total words, mean and median words per note, a 30-day notes-per-day sparkline, an hour-of-day distribution of when you write, your most-linked notes, and your top tags.

It is deliberately observation-only. There are no streaks, no daily targets, no "you didn't write today" notifications. Stats here are a way to see your work as a body across time, not a way to discipline yourself. Some weeks you will write a lot of notes; some weeks you will spend reading and thinking and write nothing. Both are correct. The stats page reflects this without judgment.

Settings, themes, and the footer pages

The settings page (linked from the footer of every page) is where Zetteling's configurable behavior lives. There is no command-line flag, no config file you have to edit by hand for normal use — everything is a form field on /settings. The settings persist to settings.json next to the database in the app's data folder, and changes take effect immediately on save.

The main things you can configure: AI providers and models (chat and embedding slots, with API keys, base URLs, and model names — see AI features above); the notes directory (where your .md files live on disk — see Sync & backup for migration guidance); the bibliography path for the Zotero/Pandoc integration (see Citations); the HTML sanitization toggle (see Trust model); and a few smaller knobs you can discover by visiting the page.

Themes. The footer has a theme button that cycles between system, light, and dark. The choice persists in your browser's localStorage (a single key, no other data stored client-side). It is not synced across devices and does not touch the server. If you've cleared your browser data or are running Zetteling for the first time, you'll get the system default — which itself follows your OS's prefers-color-scheme setting on every modern browser and on the BeeWare desktop window.

The footer pages. Below every page you'll find links to: about (version number, changelog, attribution), settings, privacy (the complete account of what data goes where), license (PolyForm Noncommercial 1.0 — free for noncommercial use, see the page for the full terms), and the about page again. The version number in the footer is also a link to the about page, which is the easiest way to check what release you're running and what shipped in it.

Sync and backup

The corpus is a folder full of plain text files. Every backup tool ever invented works on it: Time Machine, rsync, Git, Dropbox, iCloud Drive, Syncthing. Two recommendations in particular, but first an important note about where your notes actually live on disk.

Where Zetteling stores your notes by default. Out of the box, Zetteling stores notes inside its application-data folder, in the platform-standard location for whichever operating system you are on (Library/Application Support on macOS, ~/.local/share or equivalent on Linux, AppData on Windows). The exact path on your machine is shown at the top of the settings page next to notes directory. This default is fine for daily use but awkward for syncing: it tends to be a hidden system path most sync tools refuse to traverse by default, and it sits next to zettel.db and settings.json, which must NOT be synced. If you only ever use one machine and only want backups (Time Machine, Git), you can leave notes where they are and skip the migration steps below. If you want to sync your notes across machines, migrate first.

Migrating your notes to a sync-friendly location. Zetteling does not move your notes for you when you change the setting — it only updates where it looks for notes on next launch. You have to copy the files yourself before flipping the setting, or you will open Zetteling to an empty corpus and briefly believe you have lost everything. Here is the safe sequence:

  1. Decide where you want your notes to live. Good options include ~/Documents/Zetteling/notes, ~/Zetteling/notes, or ~/notes — anywhere your sync tool can reach without permission contortions. Create the parent directory if needed.
  2. Quit Zetteling completely (close the window AND quit from the dock or system tray).
  3. In your file manager or a terminal, copy the entire contents of your current notes folder (the path shown on the settings page) into your chosen new location. Use copy, not move, so you have a fallback if anything goes wrong.
  4. Launch Zetteling again. Open the settings page, set the notes directory field to your new path, and save. The page will tell you the change won't take effect until restart.
  5. Quit and relaunch Zetteling.
  6. Verify your notes are all visible — the count on the home page should match what you had before.
  7. Once you have confirmed everything is in the new location and Zetteling is reading from it correctly, you can delete the original copy in the application-data folder. Don't delete it on the same day you migrate. Wait a week.

From here on, every reference to "your notes folder" in this section means whatever path you set in step 4.

Backup: use Git for version history

From inside your notes folder, run:

git init
git add .
git commit -m "initial commit"

Then commit periodically — daily, weekly, whatever rhythm you like. You get free undo for everything you've ever written. To see the history of any single note:

git log -p 20260407164313-mynote.md

This is independent of the soft-delete trash and works even if the whole notes folder gets accidentally destroyed. For convenience, you can wire up a cron job or a launchd plist to auto-commit nightly.

Sync: use Syncthing for multi-device access

Syncthing is a free, open source, end-to-end encrypted, peer-to-peer file sync tool. It mirrors a folder between two or more devices without any central server. The architecture of Zetteling is local-first: each device runs its own copy of the app pointing at its own copy of the notes folder, and Syncthing keeps the notes folders in agreement.

Critical rule: sync only your notes folder (the path you set in notes directory on the settings page). Never sync the application-data folder containing zettel.db and settings.json — the database is per-machine and rebuilds itself from the notes; sharing it across devices would corrupt it. The settings file contains API keys and machine-specific preferences. Sync the notes folder only, nothing else.

Step 1 — Install on your Mac:

brew install syncthing
brew services start syncthing

Open http://127.0.0.1:8384 in any browser. You should see the Syncthing GUI. This is your local Syncthing's control panel.

Step 2 — Install on your VPS: SSH into the VPS and run:

sudo apt update
sudo apt install -y syncthing
sudo loginctl enable-linger $USER
systemctl --user enable syncthing.service
systemctl --user start syncthing.service

The enable-linger command lets the service keep running after you log out of SSH. The Syncthing GUI on the VPS only listens on localhost for security, so to access it from your Mac, open an SSH tunnel:

ssh -L 8384:127.0.0.1:8384 your_user@your.vps.example.com

While that SSH session is open, visit http://127.0.0.1:8384 on your Mac — you're now talking to the VPS's Syncthing GUI through the tunnel. (If your Mac's own Syncthing is also using port 8384, use a different local port: ssh -L 8385:127.0.0.1:8384 ... and visit :8385.)

Step 3 — Pair the devices. Each Syncthing instance has a unique Device ID (a long string like A1B2C3D-...).

  1. On the Mac GUI: click Actions → Show ID and copy the device ID.
  2. On the VPS GUI (via tunnel): click Add Remote Device, paste the Mac's ID, give it a name like "Mac Mini", and save.
  3. Back on the Mac GUI: a notification appears asking whether to add the VPS as a remote device. Accept it.

Step 4 — Share the notes folder:

  1. On the Mac GUI: click Add Folder. Set Folder Path to the absolute path of your Zetteling notes directory (e.g. /Users/you/Documents/Zetteling/notes). Give it a label like "zetteling-notes". In the Sharing tab, tick the box next to your VPS device. In the File Versioning tab, choose Staggered File Versioning with default settings. Save.
  2. On the VPS GUI: a notification appears asking whether to accept the new folder share. Click Add, then set the folder path to wherever you want Zetteling's notes to live on the VPS. Save.

Within a minute, every .md file from your Mac will appear on the VPS, and the watcher on each side will pick up changes automatically. Conflict files (if two devices edit the same note simultaneously) are saved as .sync-conflict-... files alongside the original — nothing is ever silently lost.

Optional: sync your bibliography too. If you use the Zotero/BibTeX integration, put the .bib file inside the same Syncthing folder so it travels with your notes.

Troubleshooting

I edited a file in vim/Obsidian and the web UI doesn't show my changes
Reload the page. The watcher updates the index in the background but the page itself doesn't auto-refresh. If a reload doesn't show the change, check that you saved the file directly inside your notes directory (the path shown on the settings page) and not in a subdirectory.
Search returns no results for words I know are in my notes
The index may be out of sync. Quit Zetteling completely, delete the database file zettel.db (it lives in the application-data folder; the exact path is shown at the top of the settings page next to notes directory), and relaunch. The watcher does a full reconciliation on startup and rebuilds the index from your notes folder. This is always safe — the database is disposable and contains nothing your notes don't.
A wikilink shows as broken even though the note exists
The link must use the destination note's exact 14-digit ID, not its title or filename. Find the destination note, look at its URL or the small id shown under its title, and use that exact number.
The citation picker doesn't appear when I type @
You don't have a bibliography configured. Open the settings page and set the bibliography path field to point at your .bib file. See Citations above for the full setup walkthrough.
AI features show "no provider configured" or just don't appear
You haven't set up an AI provider. Open the settings page, pick a chat provider and/or an embeddings provider from the dropdowns, supply an API key (or leave it blank for Ollama), and click Test to verify. Until at least one provider is configured, the Interrogate button, the Suggest tags button, and the related-notes panel all stay dormant. See AI features above for the full walkthrough.
Ollama errors with "connection refused" or "is the Ollama server running?"
Ollama is configured but its server isn't running. In a terminal, run ollama serve and leave it running, then retry the AI feature. If ollama serve isn't installed, install Ollama from ollama.com first. If the server is running but Zetteling still can't reach it, check the base URL on the settings page — it should be http://127.0.0.1:11434 for a local install.
Ollama errors with "model not found" or "try pulling"
The model name you configured doesn't match anything you've downloaded. In a terminal, run ollama list to see what's actually available, then either change the model name on the settings page to match one of those, or run ollama pull <model-name> to download the one you want. Common gotcha: configuring a chat model (like qwen2.5:14b) in the embeddings slot, or vice versa. Embeddings need a dedicated embedding model like nomic-embed-text.
I want to start completely fresh
Quit Zetteling. Delete zettel.db from the application-data folder (path shown on the settings page) and, if you want a truly empty corpus, move your notes folder aside. Relaunch. You'll get an empty Zettelkasten that rebuilds itself from whatever notes remain.
Something is broken in a way not covered here
If you launched Zetteling from a terminal (via briefcase dev or as a Flask server directly), check the terminal output — most errors print useful information there. For the packaged desktop app, BeeWare logs are written to the application-data folder. As a first move, quit and relaunch Zetteling — many transient problems (file watcher hiccups, stale connections) clear up.
