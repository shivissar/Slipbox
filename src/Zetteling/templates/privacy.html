Privacy

Zetteling collects no data about you. There is no telemetry, no analytics, no crash reporting, no update check, no "phone home." The Flask server binds to 127.0.0.1 and only accepts connections from your own machine.

However, Zetteling can optionally send your note content to AI services that you explicitly configure. This page is a complete account of what gets sent where, under which circumstances, and how to turn it off.

What stays on your machine no matter what

Your notes, your bibliography, your settings, the full-text search index, the semantic search vector index, the chat history for note interrogation, the trash, the SQLite database — every byte of every thing this app touches lives in the project folder on your own disk and goes nowhere else except via the specific AI-feature paths listed below, which only activate if you've configured a provider.

What gets sent over the network from the page itself

Nothing. Since v5.0 every script, stylesheet and font the app uses ships inside it: HTMX (static/vendor/htmx-1.9.12.min.js) and the fonts (static/fonts/, each under the SIL Open Font Licence) load from your own disk. Earlier versions fetched HTMX from unpkg.com on uncached page views; that request no longer exists, and live search now works offline.

One exception applies only if you run Zetteling on a server rather than as the desktop app: if you deploy it behind Caddy with HTTPS, certificate provisioning involves Let's Encrypt's ACME servers. That is a Caddy operation, not a Zetteling one, and happens only on first start and at renewals.

What Zetteling stores in your browser

One small disclosure for completeness: hiding the side panel writes a single key (zettel-rail-hidden, value "1" or absent) to the page's localStorage, so the panel stays hidden next time. That is the entire client-side storage footprint — no cookies, no session storage, no IndexedDB, no fingerprinting. Your theme, fonts and other appearance choices are not stored in the browser; since v5.0 they are saved in settings.json with your other settings, on your own disk.

AI features and what they transmit

If no AI provider is configured: nothing is transmitted, ever. The entire AI subsystem stays dormant unless you pick a provider and supply credentials on the settings page. You can verify this by leaving the provider dropdowns on "none" — the AI features will simply refuse to run.

If you do configure a provider, here is every path through which note content can leave your machine, and exactly which feature triggers which path:

Which features send data, and when

Semantic search / find-related-notes (M4.2)
This is the only feature that sends data automatically, without a per-request button click. When a semantic-search embed provider is configured, every note save triggers an embedding request: the note's title and body are sent to the embed provider, which returns a vector that's stored in your local database. The vector is stored locally; only the text is transmitted. If you create or edit 50 notes in a session with an embed provider active, that's 50 embedding requests. To turn this off completely, set the embed provider to "none" on the settings page — the Related list in the side panel will show a short note instead, and no other feature is affected.
Note interrogation / chat (M4.3)
Triggered only when you open the Interrogate tab in a note's side panel and send a message. Each message sends the note's full text plus your conversation history so far to the chat provider. The conversation is kept in a module-level Python dict in memory only — never written to disk, never logged — and is lost whenever the underlying Python process exits. In the desktop app that happens at every launch; in a long-running Flask deployment it persists until the process is killed or restarted. To use this feature without any network transmission, configure Ollama as your chat provider — everything stays on your hardware.
Tag suggestions (M4.4)
Triggered only when you click "Suggest tags" on the editor form. The note's title, the first 4,000 characters of its body, and the full list of your existing tags are sent to the chat provider. The response is filtered against your existing vocabulary so the model cannot invent new tags. One request per button click; never automatic.
Test connection button (settings page)
Triggered only when you click "Test" next to a provider field on the settings page. Sends a minimal "say hello" request to the configured endpoint to verify the API key works. No note content is involved.

Everything outside of these four paths happens locally. Full-text search is SQLite FTS5. Wikilinks, backlinks, threads, tags, the bibliography picker, export to Word/PDF, stats — all local, all the time, regardless of AI configuration.

Anthropic (Claude)

Requests go to api.anthropic.com. Your API key is sent in an HTTP header. Anthropic's data handling policy is documented at anthropic.com/legal/privacy and varies by API tier; generally Anthropic does not train on API inputs by default, but this is subject to change and you should read their current policy before sending sensitive material.

OpenAI-compatible providers (OpenAI, OpenRouter, Together, Groq, DeepSeek, and others)

Requests go to whichever base URL you configure. Your API key is sent in the Authorization header. Data handling depends entirely on which provider you point at — read their privacy policies before using sensitive material. Some of these providers train on API inputs by default; some retain data indefinitely. The convenience of a single OpenAI-compatible interface across providers comes at the cost of policy heterogeneity, and Zetteling cannot tell you what any given provider does with your data.

Google Gemini

Requests go to generativelanguage.googleapis.com via the official google-genai SDK. Your API key is sent as a query parameter or header depending on the endpoint. Google's data handling policy for the Gemini API is documented at ai.google.dev/gemini-api/terms. Note especially that the free tier of Gemini allows Google to use your inputs for product improvement. If you are on the free tier and your notes contain unpublished research, interview transcripts, IRB-sensitive material, or anything else that should not leave your control, use a paid tier or switch to Ollama.

Ollama (local)

Nothing leaves your machine. Ollama runs the model on your own hardware, so when you trigger an AI feature with Ollama configured the request goes from Zetteling to 127.0.0.1:11434 (or whatever local URL you specified) and stays there. The API key field is unused. This is the privacy-correct option for sensitive material, at the cost of speed and model size — local models are smaller and slower than top-tier cloud models, but a Mac Mini M4 can run a 7B–14B parameter model comfortably for both chat and embeddings. You can mix providers: use Ollama for embeddings (which run constantly) and Anthropic or Gemini for chat (which runs occasionally), or any other combination.

Voyage AI (embeddings only)

Requests go to api.voyageai.com. Your API key is sent in the Authorization header. Voyage AI is a third-party embeddings provider; Anthropic does not currently offer first-party embedding models, so Voyage is one common pairing for Claude users. (Voyage was acquired by MongoDB in 2025; check current ownership and policy before sending sensitive material.) Voyage's data handling policy is documented at voyageai.com/privacy and should be read before sending sensitive material. Voyage is embeddings-only — it will not work for chat, note interrogation, or tag suggestions, only for the semantic related-notes feature.

How API keys are stored

All API keys are stored in plain text in settings.json in the project directory, alongside your other settings. There is no good way to encrypt-at-rest in a self-hosted single-user app without forcing you to enter a password every launch, which would be worse UX than the problem it solves. The mitigation: settings.json stays on local disk, in the project folder, and should not be synced to cloud storage. The cloud-backup section of the README recommends syncing only the notes/ folder, not the project root. If you do want to back up settings, back them up to an encrypted local disk.

The privacy policy in one sentence

Nothing leaves your machine unless you configured an AI provider and either clicked an AI button or saved a note with semantic-search embedding enabled; everything else is entirely local, forever, and without exception.

Trust model and when it breaks

Zetteling's default assumption: you are the sole author of every note in your corpus. All markdown rendering, all AI operations, all search indexing, all export flows treat notes as content you wrote and therefore trust. This assumption is correct for the default single-user local install and keeps the app simple.

The assumption is violated, silently and without warning, by each of the following workflow changes. Each one has a mitigation.

Importing external markdown

If you copy-paste a markdown file from someone else, or bulk-import an old Evernote, Obsidian, or Notion export, or accept a collaborator's research notes — the imported content is no longer self-authored. A malicious note could contain embedded HTML or JavaScript that runs in your browser when you view it, which could then use Zetteling's own API to read, modify, or delete other notes.

Mitigation: enable sanitize_note_html on the settings page before importing external content. This strips dangerous HTML while keeping safe markdown features.

Syncing notes with another person via Syncthing

Same problem as imports, just continuous. If you share a Syncthing folder with a research partner, their notes appear in your corpus and become inputs to all of Zetteling's features.

Mitigation: enable sanitization, plus a conversation with your collaborator about what they put in shared notes.

Exposing Zetteling remotely via Caddy or another reverse proxy

Even with basic auth, the web interface becomes reachable from somewhere other than loopback. Two concerns come into play: session tampering and cross-site request forgery. An attacker who gets you to visit a malicious page while you are logged in could trigger POSTs to Zetteling using your browser's authenticated session.

Mitigation: set ZETTEL_SECRET_KEY to a strong random value (Zetteling logs a warning at startup if you have not), enable sanitization, and prefer deployment behind an authenticating proxy that strips cross-origin POSTs. For single-user remote use, the Caddy basic-auth setup in the README is the minimum acceptable configuration.

Publishing notes to a public web view

Zetteling does not currently support this, but if you ever build an export-to-static-site pipeline from your corpus, every visitor to the published site becomes a potential XSS victim for any untrusted content that found its way into your notes. This matters even if only ONE note was imported from somewhere else months ago and you forgot about it.

Mitigation: sanitize at publication time, regardless of what the source notes look like.

Feeding notes into an LLM pipeline (local or cloud)

Notes you trust may contain prompt-injection payloads intended to manipulate the LLM into ignoring its instructions or exfiltrating other content. This is an emerging concern across the whole personal-knowledge- management space, not specific to Zetteling. Worth being aware of if you start using the Interrogate feature on imported notes.

Mitigation: treat untrusted notes as you would treat untrusted user input in any other LLM application. There is no airtight technical defense against prompt injection today.

Using Pandoc export on untrusted notes

Pandoc can execute raw LaTeX, which can run arbitrary commands. If you export a note containing crafted LaTeX to PDF, you are running someone else's code. The same caveat applies to other output formats that allow embedded scripting.

Mitigation: do not export untrusted notes to formats that allow embedded code. Export to plain text or sanitized HTML instead.

Zetteling's design philosophy is that the default state should be simple and the hardening should be explicit and opt-in, rather than defending against adversaries you do not have. This section exists so the moment you do have them, you know what to change.
