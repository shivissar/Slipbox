Privacy

Verweis collects no data about you. There is no telemetry, no analytics and no crash reporting. The one thing Verweis does over the network on its own is an optional daily update check, which tells GitHub your IP address and the app’s version number and nothing else. The Flask server binds to 127.0.0.1 and only accepts connections from your own machine.

However, Verweis can optionally send your note content to AI services that you explicitly configure. This page is a complete account of what gets sent where, under which circumstances, and how to turn it off.

What stays on your machine no matter what

Your notes, your bibliography, your settings, the full-text search index, the semantic search vector index, the chat history for note interrogation, the trash, the SQLite database — every byte of every thing this app touches lives on your own disk (the notes in your notes folder, everything else in the app-data folder, ~/Library/Application Support/com.shivissar.verweis/) and goes nowhere else except via the specific AI-feature paths listed below, which only activate if you've configured a provider.

What gets sent over the network from the page itself

Nothing. Since v5.0 every script, stylesheet and font the app uses ships inside it: HTMX (static/vendor/htmx-1.9.12.min.js) and the fonts (static/fonts/, each under the SIL Open Font Licence) load from your own disk. Earlier versions fetched HTMX from unpkg.com on uncached page views; that request no longer exists, and live search now works offline.

One exception is in your hands: a note that shows an image from a web address (![](https://…)) loads it from that site whenever the note is shown, which tells the site your IP address and when you looked.

The update check

Since 5.2, Verweis asks GitHub once a day whether a newer version has been published. It is on unless you untick it on the first-run screen or turn it off in Settings → Updates; with it off, Verweis asks only when you press Check now.

  • Where it goes: one HTTPS request to api.github.com, for the latest release of shivissar/Verweis, without any GitHub account or key.
  • What it carries: your IP address (every internet request does) and a header saying Verweis/{{ version }}. No notes, titles, settings, file names or identifiers.
  • What comes back: the newest release’s version number, date, notes and download link. Verweis stores these in settings.json and shows a notice if the version is newer than yours.
  • What it never does: download or install anything. Download and release-page buttons open in your browser, and you install the new version yourself, so macOS checks it as it did the first time.

GitHub’s handling of those requests is covered by the GitHub General Privacy Statement.

What Verweis stores in your browser

One small disclosure for completeness: hiding the side panel writes a single key (zettel-rail-hidden, value "1" or absent) to the page's localStorage, so the panel stays hidden next time. That is the entire client-side storage footprint — no cookies, no session storage, no IndexedDB, no fingerprinting. Your theme, fonts and other appearance choices are not stored in the browser; since v5.0 they are saved in settings.json with your other settings, on your own disk.

AI features and what they transmit

If no AI provider is configured: nothing is transmitted, ever. The entire AI subsystem stays dormant unless you pick a provider and supply credentials on the settings page. You can verify this by leaving the provider dropdowns on "none" — the AI features will simply refuse to run.

If you do configure a provider, here is every path through which note content can leave your machine, and exactly which feature triggers which path:

Which features send data, and when

Semantic search / find-related-notes (M4.2)
This is the only feature that sends data automatically, without a per-request button click. When a semantic-search embed provider is configured, a note is sent for embedding each time you finish editing it (leaving the editor, pressing ⌘S, or quitting), not on every autosave: its title and text go to the embed provider, which returns a vector that's stored in your local database. This happens in the background, after the note is saved. Unchanged notes aren't sent again. If you edit 50 notes in a session with an embed provider active, that's about 50 embedding requests. Locked notes are never sent. To turn this off completely, set the embed provider to "none" on the settings page — the Related list in the side panel will show a short note instead, and no other feature is affected.
Note interrogation / chat (M4.3)
Triggered only when you open the Interrogate tab in a note's side panel and send a message. Each message sends the note's full text, with any notes it embeds (![[…]]) written out in full, plus your conversation history so far to the chat provider. Embedded locked notes are left out and replaced by a line saying a locked note was there; a locked note itself can't be interrogated. The conversation is kept in a module-level Python dict in memory only — never written to disk, never logged — and is lost whenever the underlying Python process exits. In the desktop app that happens at every launch; in a long-running Flask deployment it persists until the process is killed or restarted. To use this feature without any network transmission, configure Ollama as your chat provider — everything stays on your hardware.
Tag suggestions (M4.4)
Triggered only when you click "Suggest tags" on the editor form. The note's title, the first 4,000 characters of its body, and the full list of your existing tags are sent to the chat provider. The response is filtered against your existing vocabulary so the model cannot invent new tags. One request per button click; never automatic.
Test connection button (settings page)
Triggered only when you click "Test" next to a provider field on the settings page. Sends a minimal "say hello" request to the configured endpoint to verify the API key works. No note content is involved.

Everything outside of these four paths happens locally. Full-text search is SQLite FTS5. Wikilinks, backlinks, threads, tags, the bibliography picker, export with pandoc (Word, OpenDocument, LaTeX, HTML, EPUB), the codebook, stats — all local, all the time, regardless of AI configuration.

Anthropic (Claude)

Requests go to api.anthropic.com. Your API key is sent in an HTTP header. Anthropic's data handling policy is documented at anthropic.com/legal/privacy and varies by API tier; generally Anthropic does not train on API inputs by default, but this is subject to change and you should read their current policy before sending sensitive material.

OpenAI-compatible providers (OpenAI, OpenRouter, Together, Groq, DeepSeek, and others)

Requests go to whichever base URL you configure. Your API key is sent in the Authorization header. Data handling depends entirely on which provider you point at — read their privacy policies before using sensitive material. Some of these providers train on API inputs by default; some retain data indefinitely. The convenience of a single OpenAI-compatible interface across providers comes at the cost of policy heterogeneity, and Verweis cannot tell you what any given provider does with your data.

Google Gemini

Requests go to generativelanguage.googleapis.com via the official google-genai SDK. Your API key is sent as a query parameter or header depending on the endpoint. Google's data handling policy for the Gemini API is documented at ai.google.dev/gemini-api/terms. Note especially that the free tier of Gemini allows Google to use your inputs for product improvement. If you are on the free tier and your notes contain unpublished research, interview transcripts, IRB-sensitive material, or anything else that should not leave your control, use a paid tier or switch to Ollama.

Ollama (local)

Nothing leaves your machine. Ollama runs the model on your own hardware, so when you trigger an AI feature with Ollama configured the request goes from Verweis to 127.0.0.1:11434 (or whatever local URL you specified) and stays there. The API key field is unused. This is the privacy-correct option for sensitive material, at the cost of speed and model size — local models are smaller and slower than top-tier cloud models, but a Mac Mini M4 can run a 7B–14B parameter model comfortably for both chat and embeddings. You can mix providers: use Ollama for embeddings (which run constantly) and Anthropic or Gemini for chat (which runs occasionally), or any other combination.

Voyage AI (embeddings only)

Requests go to api.voyageai.com. Your API key is sent in the Authorization header. Voyage AI is a third-party embeddings provider; Anthropic does not currently offer first-party embedding models, so Voyage is one common pairing for Claude users. (Voyage was acquired by MongoDB in 2025; check current ownership and policy before sending sensitive material.) Voyage's data handling policy is documented at voyageai.com/privacy and should be read before sending sensitive material. Voyage is embeddings-only — it will not work for chat, note interrogation, or tag suggestions, only for the semantic related-notes feature.

How API keys are stored

API keys are stored unencrypted in settings.json (and its backup copy, settings.json.bak) in the app-data folder (~/Library/Application Support/com.shivissar.verweis/), with your other settings. That folder is separate from your notes, so syncing or backing up the notes folder doesn’t copy your keys. Don’t add the app-data folder to a sync service, and treat any backup of it as you would the keys themselves (Time Machine backups are encrypted if you turn that on). Anyone who can read files in your user account can read the keys; FileVault protects them when the Mac is off.

Locked notes

If you lock a note, its text is encrypted on your Mac with AES-256-GCM before it is written to disk, under a key protected by your password (Argon2id) and by a recovery key only you hold. A locked note’s text is never sent to any AI provider, never added to the search index and never used for related notes. Its title, tags, kind, threads and dates stay in plain text. Neither your password nor the decrypted text is ever written to disk. See Help → Locked notes for the details and the limits.

Note history, templates and the codebook

Earlier versions of your notes are kept on your Mac in the app-data folder (history/), never sent anywhere. Versions of locked notes are encrypted like the notes themselves. Templates (.templates/) and code definitions (.verweis-codebook.json) are files in your notes folder. Coded passages from locked notes are read only while locked notes are open and are never written to the search index.

The privacy policy in one sentence

Your notes leave your machine only if you configured an AI provider and either clicked an AI button or saved a note with semantic-search embedding enabled; apart from that and the optional daily update check, which carries nothing from your notes, everything is local.

Trust model and when it breaks

Verweis is built for one person on their own Mac. It doesn’t assume you wrote every note, though: notes arrive from imports, shared folders and the web, and since 5.2 the defaults are safe for those.

  • Sanitising is on by default. When a note is shown, scripts, event handlers, javascript: links and other active HTML are removed; Markdown formatting, images, tables, footnotes and coded passages keep working. Turn it off in Settings → Writing only if you rely on raw HTML in notes you wrote yourself.
  • Only Verweis’s own scripts run. Every page carries a content security policy that refuses any other script, sanitising or not.
  • Only its own window can make changes. The local server answers only to 127.0.0.1 and localhost (so a web page can’t reach it under another name), and refuses changes sent from other web pages, even ones open in your browser on the same Mac.

What these don’t cover:

Exporting notes you didn’t write

Exports are made by pandoc from the note’s Markdown, not from the sanitised page. An HTML export keeps any HTML in the note, scripts included, and runs them when opened in a browser; a LaTeX export keeps raw LaTeX, which can run commands if you compile it with shell escape turned on. Read such exports before opening or compiling them, and sanitise an HTML export before publishing it anywhere.

Sending notes you didn’t write to an AI provider

A note can contain text written to steer a language model (“ignore your instructions and…”), known as prompt injection. With Interrogate, the worst a note can do is mislead the conversation about itself and the notes it embeds, since nothing else is sent; tag suggestions only accept tags you already use. There is no complete technical defence against prompt injection; read answers about imported notes with that in mind.

Turning sanitising off

With sanitising off, HTML in a note is shown as written. The content security policy still stops inline and outside scripts, but other active content (forms, frames, styles that hide or imitate parts of the page) gets through. Keep it on if any note in your folder came from someone else.

Running Verweis on a server

Verweis is a desktop app and has no accounts or login. If you run its Flask server on another machine anyway, anyone who can reach it can read and change every note. Put it behind a reverse proxy that requires authentication, set ZETTEL_TRUSTED_HOSTS to the names it is reached by and ZETTEL_BEHIND_PROXY=1, and don’t use locked notes there: while they’re open, the server shows their text to anyone who can reach it.
